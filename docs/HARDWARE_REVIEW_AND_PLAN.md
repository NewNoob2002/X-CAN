- 首版故障注入为“定时显性脉冲，观察错误与恢复”。

**结论：现有硬件在拓扑和引脚分配上具备实现这一首版的条件，值得继续做样板验证；暂未发现必须整体重做才能开展首版的架构性问题。这不是电气验收通过。**

首版定位：单通道、USB 联机的 CAN/CAN-FD 帧分析仪，支持有界的显性脉冲注入、错误事件记录和恢复观察。先做普通收发与监听，再开放注入。不把指定 ID 的同帧位级修改、完整错误帧波形解码、物理短路/断线或无限时长显性保持纳入首版。

时钟先追求可验证：采用与实装 12 MHz HSE 相符的配置，分别校核 CPU、FDCAN、TIM2、TIM3、USB 的实际时钟。当前 LED 固件实读 PLL 的 M=3、N=85、R=2，对应 170 MHz；这是按标称晶振和寄存器计算，不是频率实测。CPU 超过 150 MHz 时需要 Range 1 boost，不能只修改 PLL 倍频。[S9 §3.11.3] USB 可以使用 HSE 驱动 PLL 产生的精确 48 MHz，或 HSI48 + CRS 自动校准；需重新联合规划各路时钟，不能假定当前 LED 固件的 PLL 已提供 USB 48 MHz。本板无 LSE，HSI48 路线可用 USB SOF 同步。不能将未校准的 HSI48 当作全条件精度保证。[S9 §3.34–3.36][S10 §7.2.3、§8]

驱动核对后，首轮优先采用 HSE/PLL 产生 USB 48 MHz：所查 G4 时钟路径没有自动完成 CRS 校准。若改用 HSI48，需明确实现 CRS / USB SOF 校准；所供 datasheet 表86对 crystal-less USB 给出的温度范围为 −15 至 +85 °C，不能沿用芯片总体工作温度承诺。[S9 p159；本次驱动核对报告]

### 2.2 USB：Type-C 数据与供电

图上有 CC1/CC2 各自的 5.1 kΩ 下拉、正反插 D+/D− 汇接、USBLC6-2SC6 防护、VBUS 自恢复保险丝和 TVS，PA11/PA12 接 USB。基本连接符合本项目 USB 设备的意图，未看到明显的 D+/D− 对调。[S1 p1–p2]

样板检查：

1. 正反插分别验证供电、枚举及持续数据传输。
2. 测 USB 接口 VBUS、保险丝后的 5V_SYS 及 U2 VCC，特别关注发显性位时的压降。U2 推荐 VCC 范围为 4.5–5.5 V。[S2 §6.3、§9.4]
3. 确认 D1、D3 实际型号、方向及焊接，检查 USB 差分布线与保护器件位置。
4. 验证主机暂停读取、挂起、复位、拔插后的固件状态及注入退出行为。
5. 本图没有独立 VBUS 检测信号接到 MCU；以 USB 总线供电设备设计首版，AN4879 §2.6 明确此情形不强制独立 VBUS sensing。若以后使用外部 3.3 V 供电，需重新处理 VBUS 检测和反向供电，不能直接沿用该假设。[S1][S14 p11]

已确认：G431 内置 D+ 上拉，数据手册表86脚注明确无需外加 D+/D− 终端串联电阻，输出匹配已集成。原理图这两点无需补件。USB 完整电气规格要求 VDD 为 3.0–3.6 V；不能以 MCU 能在更低电压运行作为 USB 合格依据。USB FS 的 12 Mbit/s 是链路速率，不是应用有效吞吐承诺。[S9 §3.34、p159 表86]

### 2.3 POWER：5 V 转 3.3 V

AMS1117-3.3 配有输入、输出电容及电源 LED，图中连接具备基本稳压条件。[S1 p3]

- 需要确认 AMS1117 的实际厂商、输出电容材质/ESR 和布局，不能仅凭通用料号认定稳定性。
- 热预算按 `P ≈ (5 V − 3.3 V) × I3V3` 估算；例如 100 mA 时约 0.17 W，200 mA 时约 0.34 W。这是估算，不是本板实测负载。
- 在 CPU、USB 和 CAN 同时工作时测电流、温升、3.3 V 纹波；不预先要求更换稳压器。
- LED5 的 10 kΩ 电阻可能使指示灯较暗，属于使用体验验证项，不阻塞首版。

### 2.4 CAN：收发器、注入、捕获与终端

U2 标注 TCAN1044AVDRQ1，VCC 接 5V_SYS，VIO 接 3V3_SYS，适合本板 3.3 V 数字逻辑。采购/实物必须确认为带 **V** 的型号，不能只核对“TCAN1044A”。R10 将 STB 上拉，R4 将 FDCAN TX 上拉，R5/R6 分别将注入请求与 ARM 下拉。[S1 p4][S2 §4–§5]

根据 U7 NAND 和 U3 AND 的连接，得到：

```text
CAN_XCVR_TXD = FDCAN1_TX AND NOT(CAN1_INJECT_ARM AND CAN_Fault_Injection)
```

| ARM | 注入请求 | 收发器 TXD | 结果 |
|---|---|---|---|
| 0 | 任意 | 跟随 FDCAN1_TX | 注入被禁止 |
| 1 | 0 | 跟随 FDCAN1_TX | 普通 CAN 路径 |
| 1 | 1 | 0 | U2 正常模式下施加显性驱动 |

这与首版目标相符：输出一个有界高脉冲到 PA1，即可在 ARM 有效时请求显性注入；只能叠加显性，不能覆盖其他节点的显性为隐性。已有 ARM 门控和测试点有利于首版验证。[S1 推导][S2 §8.4.4]

需要特别处理的边界：

1. **STB=1 是待机，不是完整高速监听。** 监听时应让 U2 正常工作（STB=0），由 FDCAN 使用 listen-only 模式避免正常协议发送；注入属于显式启用的独立行为。待机 RXD 主要提供过滤后的唤醒指示，不能用于正常帧采集。[S2 §8.4]
2. **不能无限保持显性。** U2 的 TXD dominant timeout 为 1.2–4.0 ms；TXD 持续为低到达超时后会关闭驱动，恢复为高才清除该条件。首版建议将单次请求宽度上限暂定为 500 µs，并实测，不把 DTO 当作精确定时器。若 FDCAN 同时发送显性，TXD 实际连续低电平可能长于请求脉冲，故首版注入时禁止本机普通 TX。[S2 §6.8、§8.3.3；上限为项目建议]
3. **终端采用人工声明。** 用户确认两个独立拨码分别接入 120 Ω、向 PB2 声明终端状态，这是有意设计，首版保留。软件字段使用 `termination_declared`，上位机显示“120 Ω：已声明接入/已声明断开（拨码）”；按图第二拨码闭合应为高、断开由 R14 下拉为低。固件无法检测两个拨码是否一致，不将该字段用作电气自动检测结果，也不自动切换终端。[S1 p4；用户确认设计意图]
4. **PA0 捕获的是 RXD 数字边沿。** 它不是 CANH/CANL 模拟测量，无法给出总线电压、共模电压或模拟波形。[S1 推导]
5. **上电默认保护不等于运行时硬件限时保护。** 门电路在电源稳定、MCU 高阻时形成 ARM=0、注入=0、STB=1 的默认状态；运行中若 GPIO 卡住或调试暂停，仍须靠定时器单脉冲结束、看门狗和 DTO 等不同机制限制影响。实际电源上升/下降毛刺需测量。[S1 推导][S2 §8.3]
6. **不是隔离接口。** USB 地与 CAN 地共地，无隔离电源或数字隔离器。首版按共地实验台设备验证；D5 的存在不能等同于已通过整机抗扰度验证。[S1 p2–p4]

CAN-FD 建议按 500 kbit/s 仲裁 + 2 Mbit/s 数据阶段起步，再验证 5 Mbit/s。TI 描述更高的 8 Mbit/s 适用于较简单网络，不能据此承诺本板、线束和终端组合下的性能。[S2 p1；速率路线为项目建议]

## 4. Zephyr 实现方案

### 4.1 基线与板级定义

建议先固定 **Zephyr v4.4.0** 及其 west 依赖版本。已读取该 tag 的 CAN 驱动与设备树，作为规划基线；正式建工程时仍需验证工具链与最小构建。此处不是要求跟踪 `main`。[S4][S7][S8]

创建本项目独立 board 定义，参考 `nucleo_g431rb` 的 SoC 配置，不直接把其板级设置用于 X-CAN。尤其是参考板 PC4/PC5 的串口复用会与本板 STB/ARM 冲突，PA2/PA3 的控制台用途也与本板 TIM2 扩展冲突。[S1][S3]

| 信号 | MCU 引脚 | 首版用途 / 空闲状态 |
|---|---|---|
| FDCAN1_RX / TX | PB8 / PB9，AF9 | CAN 接收 / 发送 |
| CAN_RX_Capture | PA0，TIM2_CH1 AF1 | 预留短时捕获；首个脉冲版本不启用连续波形采集 |
| CAN_Fault_Injection | PA1，TIM2_CH2 AF1 | 单脉冲输出，空闲为低 |
| CAN 硬件时间戳 | TIM3 内部计数器，不需要新增引脚 | 预留恒定时间基准，连接至 FDCAN 外部 timestamp 输入 [S10 p1990] |
| CAN1_STB | PC4 | 上电为高；开始监听/收发才拉低 |

### 4.2 最小固件结构

首版只需要板级定义和 CAN 数据路径、USB 控制/数据传输、注入控制三个功能部分。优先复用 Zephyr CAN、USB、GPIO、watchdog 驱动；仅定时器的精确单脉冲行为在通用接口不够时增加小型 STM32 专用实现。不要让 Zephyr PWM/counter 驱动与专用实现同时控制 TIM2。

```text
FDCAN RX ISR → 有界接收队列 → USB 批量上传 → 主机记录/显示
主机命令 → 参数校验/状态机 → CAN 配置或有界注入事务
注入事务 → ARM + TIM2_CH2 硬件单脉冲 → 门电路 → U2
CAN 状态、丢帧计数、事务结果 → 主机事件记录
USART1 / RTT → 独立调试日志
```

- CAN RX 回调仅复制帧、记录时间/序号并入队，不阻塞，不做打印、解析或 USB 发送；Zephyr 官方说明回调运行于中断上下文。[S7]
- Zephyr STM32 FDCAN 驱动固定 RX FIFO0/1 各 3 个元素，不能靠改设备树随意增加硬件深度，也不能把两 FIFO 自动视作一个 6 帧 FIFO。先优化 ISR 服务与中断屏蔽时间。[S6][S8]
- 区分硬件 FIFO 丢失、软件队列丢弃和 USB/主机接收问题。硬件若只提供丢失事件标志，就上报事件数/已发生丢失，不能伪装成精确丢帧数。
- RAM 使用固定缓冲池/有界队列，首轮可从 32 个 CAN-FD 记录开始；容量按实际 `sizeof(record)` 计算，再由压力测试调整。SRAM1 起点 `0x20000000`，SRAM2 起点 `0x20004000`，CCM 系统总线别名起点 `0x20005800`，合计连续 32 KiB；DMA 访问 CCM 必须走该别名，不能使用 CPU 的 `0x10000000` 直连地址，也不能把两处地址当作两份 RAM 重复分配。[S9 p18][S10 §2.4]
- USB 按用户要求采用 Vendor-specific 接口，首版规划一对 Bulk OUT / Bulk IN；控制命令与帧数据按消息类型复用，日志留在 USART1/RTT。二进制协议显式定义版本、长度、类型、请求 ID/序号与字节序，不直接传输 C/Rust 内存结构。[S8 USB；接口与协议为项目设计]
- 普通帧、状态事件、注入事件携带时间来源说明。bring-up 可暂用 MCU 单调时间记录回调时间，明确不是 SOF；正式帧时间戳预留 TIM3：`FDCAN_TSCC.TSS=10b` 读取 `TIM3_CNT[15:0]`，在帧开始时锁存。CAN-FD 内部 timestamp 随仲裁/数据位时间变化，不可直接作为固定微秒计数。[S10 p1965、p1990–1991]
- TIM3 可先按 1 MHz 时基设计，16 位每 65.536 ms 回绕；扩展时间必须处理空闲期间多次回绕、FIFO 延迟及读数竞争，不能只比较相邻帧的 16 位大小。发生超出重建边界的拥塞时应标记时间不确定。先核对锁定版 Zephyr 的 external timestamp counter 支持，再接入，不占用 TIM2 的注入计数器。

Rust 上位机与固件同步推进：

- Windows 规划 WinUSB 接口绑定，Linux 规划用户态 USB 访问及设备权限配置；在双平台最小样例中先验收安装/权限流程，再开发完整业务。Windows 的免手工绑定描述符方案与所选 Zephyr 版本的实现细节需核对，不能只验证枚举就宣称双平台可用。
- 共用协议编解码与业务逻辑，USB 后端选择在实现前根据 Windows/Linux 支持核实；本阶段不锁定未经验证的 Rust USB crate 或 GUI 框架。
- 最先交付 Rust 命令行验收工具：设备枚举、按序列号打开、协议版本/能力查询、终端声明读取、帧流接收、状态查询和单次注入命令。随后接入桌面 UI；UI 功能和工期另行明确。
- 协议必须处理拆包/合包、消息长度上限、未知命令/版本、断连重连、请求超时和有界排队。Bulk 数据拥塞时控制响应不能长期饿死；主机超时不重发物理注入，重连不重放旧事务。
- 在 Windows/Linux 分别测试持续接收、主机停读、多设备区分、拔插重连和错误退出。协议编解码保留共享测试向量，校核 C 与 Rust 字段解释一致。

### 4.2.1 USB 首轮验收范围

先冻结 Vendor 接口描述符、端点方向、设备序列号、协议版本与消息头；使用项目可合法使用的 VID/PID。用最小 Rust 工具在两种系统完成设备打开和 Bulk 双向回环，再接入 CAN 数据。USB 固件、主机工具和协议定义属于同一个验收阶段，不将双平台兼容性留到最后。

### 4.3 注入事务与时序

首个实现为软件发起的 TIM2_CH2 单脉冲：向上计数、PWM mode 2、非反相输出、`OPM=1`、`UDIS=0`，软件置 CEN 启动，计数溢出更新后自动停止并回到低电平。使用独立定时器配置，`SMS=0`、`MSM=0`，不使用级联 reset+trigger，也不使用运行中连续改 CCR 的 toggle 方式。[S10 §30.4.15][S11 §2.8.1–2.8.2][S13 §3.1]

启动条件为 `CNT=0 < CCR2 ≤ ARR`。设计数 tick 为 `T`，目标延迟为 D 个 tick、脉宽为 W 个 tick，则配置 `CCR2=D`、`ARR=D+W−1`，D/W 均需至少 1，且不能溢出 32 位范围。AN4776 p36 明确宽度为 `ARR−CCR+1` 个 tick；RM0440 p1331 的文字简写省略了 +1，编码时需按计数溢出语义和 AN4776 图19处理，并用边界测试及波形确认，避免一 tick 偏差。

配置预装载及 UG 时保持 ARM=0，加载完成、清除旧事件、确认输出低后才 ARM 并启动。取消时先撤 ARM，再停止计数并恢复输出；仅清 CEN 可能把输出停留在脉冲中的高电平。线程、USB 命令延迟不参与脉宽控制；USB 到实际启动的延迟不承诺确定性。

首版事务参数：`delay_us`、`width_us`、事务 ID。初始只允许 `count=1`；建议延迟为 1 µs–1 s、脉宽为 1–500 µs，参数转换必须检查量化、范围及加法溢出。暂不接受零延迟以避免违反 OPM 的 `CCR2>0` 条件；最终可配置下限由测量精度决定。这些是首版范围建议，不是器件精度保证。

事务顺序：

1. 校验范围、当前模式及会话；拒绝本机仍有普通 TX 待完成或其他注入活动。
2. ARM 保持低，确保注入输出为低，配置定时器并清理旧事件。
3. 在 U2 正常模式且本机 FDCAN 监听条件下，置 ARM 高并启动单脉冲。
4. 定时器硬件结束脉冲；软件撤销 ARM 并返回结果。
5. 取消、异常、会话失联或看门狗复位后进入撤防状态，不自动重放注入命令。USB 超时也不视为重试许可。

状态可以保持为 `SAFE → LISTEN → INJECT_ONESHOT → LISTEN`，另设普通收发模式；注入时禁止本机普通 TX。启动默认 SAFE，启用分析时进入 LISTEN。失联先撤 ARM、停止注入，是否继续监听由会话策略决定。

验收区分“定时器执行完毕”和“总线已出现目标扰动”：只有示波器或独立接收节点能提供后者的证据；请求脉冲落在原本显性区间时，可能不产生新错误。

TIM2_CH1/CH2 共享计数器、预分频器与 ARR。首版先把 TIM2 专用于单脉冲，PA0 留作后续有界捕获；不要同时承诺持续自由运行捕获。以后增加 SOF 相对触发时，需要处理空闲识别、边沿同步、位填充、BRS 和延迟校准，重新设计定时器资源使用。FDCAN 完整帧接收回调不能用来修改已经接收完成的同一帧。

### 4.4 “观察错误与恢复”的准确含义

首版应记录：有效帧及序号、帧流中断/恢复时间、本机 CAN 状态及驱动实际可提供的错误统计、注入事务参数和执行时刻、丢失事件。不能承诺标准接收 API 返回被破坏帧的完整内容。[S7][S8]

**本机 TEC/REC 不是被测节点的 TEC/REC。** 监听模式下，本机错误统计的更新行为还需对照控制器手册和所选驱动实测；不能把“不增长”直接判为注入失败。完整验收建议使用两个正常 CAN 节点互发并 ACK，X-CAN 作为第三个监听/注入节点；通过被测节点串口/调试状态确认其错误计数、bus-off 和恢复策略。只有 X-CAN 的帧流证据时，结论应写成“通信中断/恢复”，而不是“已证明 DUT bus-off/自动恢复”。

手册已确认 MON 总线监听模式不向总线输出 ACK/主动错误显性位；不要将 ASM 受限模式误作监听，因为 ASM 仍会 ACK。RM0440 对 TEC/REC 冻结的明确描述针对 ASM，不能直接移用于 MON。[S10 p1962]

错误记录还有读取副作用：`ECR.CEL` 读后清零，`PSR.LEC/DLEC` 读后变为“无变化”，且 FD 数据阶段使用 DLEC。应用和驱动不能各自轮询同一寄存器后再拼接统计；应通过驱动的一次性状态快照统一取得并累计，核查现有驱动读路径后再决定是否需要最小补充。[S10 p1992–1994]

| §2.8.3–2.8.5，p17–18 | center-aligned/dithering、外部 reset+OC clear、短脉冲双向 break 的限制 | 首版不使用这些组合；不能把 TIM1 的 break/重复计数器能力假设为 TIM2 已有能力 |
| §2.15.1 FDCAN edge filtering，p26 | EFBI 开启且同步边界碰上 RX 下降沿时可能接收失同步；手册注明 standard frames 不受此项影响 | 明确保持 `FDCAN_CCCR.EFBI=0`，建工程时核查实际驱动及寄存器；验收覆盖扩展帧和 FD/BRS，不依靠重传掩盖采集问题 |
| §2.15.2 Tx FIFO 顺序，p26 | 混用 dedicated Tx buffer 和 Tx FIFO，且前者优先级较高时可能颠倒 FIFO 中两帧 | 核查所选驱动的 Tx queue/FIFO 实际模式，不引入该混用；需要主机发送顺序保证时初版只保留一个 pending TX。不能把硬件按 ID 仲裁的正常重排算作此勘误 |
| §2.16.1 USB remote wakeup，p26–27 | 设备发起 resume 后，等待首个 SOF 的时序窗口过短 | 首版不启用设备 remote wakeup；仍测试主机挂起/恢复。以后启用时按勘误核对 SUSP 中断约 3 ms 屏蔽方案，不盲抄寄存器极性描述 |
| §2.16.2 USB PMA CRC16，p27 | PMA 中附带的 CRC16 字节值错误，但 USB 硬件 CRC 检查仍正确 | 驱动只交付有效 payload，忽略附带 CRC16，不把这一项解释为 Bulk payload 必然损坏，也不因此添加无依据的重试 |

这些勘误不改变“现有硬件可继续首版开发”的结论，主要约束启动代码、驱动配置和测试。ADC/COMP/OPAMP/UCPD 等首版未启用功能的限制不列为当前阻塞；项目没有连接 UCPD CC 引脚，不因使用 Type-C 插座就启用 UCPD/PD 功能。
